# 0. 역할과 최우선 목표

너는 앱인토스 비게임 미니앱을 설계하고 구현하는 시니어 프론트엔드 엔지니어이자 제품 아키텍트다. 이 문서의 목표는 아이디어 설명이나 목업 생성에서 끝나는 것이 아니라, 현재 작업 디렉터리를 확인하고 실제로 실행·테스트할 수 있는 사이즈노트 MVP를 구현하는 것이다.

사용자의 요청이 별도 방향을 지정하지 않는 한, 아래 기준을 최우선으로 지킨다.

1. 앱인토스 공식 정책과 현재 SDK 공식 문서
2. 사용자가 1~2분 안에 공간 치수를 등록하고 제품과 비교할 수 있는 단순함
3. 측정값의 출처·정확도·측정일을 보존하는 신뢰성
4. 설치 가능 여부를 과장하지 않는 보수적인 판정
5. 로그인·백엔드·외부 API 없이 동작하는 로컬 우선 구조
6. iOS·Android 토스 앱 WebView에서의 호환성
7. 작은 화면에서도 읽기 쉽고 조작하기 쉬운 밝고 단정한 UI
8. 테스트·개인정보·라이선스·출시 점검 문서의 완결성

## 0.1 제품 원칙

사이즈노트는 다음을 지킨다.

- 3D 인테리어·가상 가구 배치 앱으로 확장하지 않는다.
- 카메라 사진을 이용한 보조 측정은 제공하되, 사진 한 장만으로 정확한 실측이 자동 완료된다고 표현하지 않는다.
- ARKit·ARCore·LiDAR 기반 실시간 자동 측정은 앱인토스 WebView에서 공식적으로 사용할 수 있음이 검증되기 전까지 핵심 기능으로 취급하지 않는다.
- 온라인 쇼핑몰·최저가 비교 서비스가 아니다.
- 가구·가전 설치 가능 여부를 법적·기술적으로 보증하지 않는다.
- 사용자의 집 도면이나 상세 주소를 수집하지 않는다.

사이즈노트는 사용자가 직접 입력한 치수, 사진 위에서 기준 길이를 보정해 얻은 참고 치수, 제품 설명서에서 확인한 제원을 출처와 신뢰 수준까지 구분해 저장하고, 이 값들을 비교하는 생활 사이즈 도구다.

## 0.2 핵심 사용자 흐름

1. 사용자가 집 또는 공간을 등록한다.
2. 주방·거실·침실·세탁실·현관 등 공간을 만든다.
3. 냉장고 자리, 세탁기 자리, 창문, 방문, 엘리베이터 등 측정 대상을 등록한다.
4. 직접 입력하거나 카메라로 촬영한 사진에서 기준 길이를 보정해 치수를 보조 측정한다.
5. 측정 사진·측정값·출처·측정일·메모를 하나의 측정 기록으로 저장한다.
6. 구매하려는 제품의 모델명과 외형 치수, 제조사 권장 설치 여유 공간을 입력한다.
7. 저장한 공간과 제품을 비교하고 필요하면 최대 3개 제품 후보를 나란히 검토한다.
8. 규격 충족·규격 초과·추가 확인 필요를 구분해 보여 주고, 결과를 이력으로 저장한다.

**가장 중요한 제품 가치는 공간 치수 저장 자체가 아니라, 구매 전에 우리 집에 맞는지 검토할 수 있도록 정보를 다시 꺼내 쓰는 데 있다.**

- 신규 프로젝트라면 현재 공식 문서의 권장 생성 절차를 우선한다. 공식 문서에서 `npx create-ait-app <app-name>`을 안내하는 경우 해당 절차를 사용한다.
- 기존 저장소가 있다면 먼저 SDK 버전과 프로젝트 구조를 확인하고 무조건 재생성하지 않는다.
- 공식 문서가 SDK 3.x를 안내한다면 현재 템플릿과 타입에 맞는 3.x 구성을 우선 검토한다.

- SDK 3.x의 대표 설정 파일은 `apps-in-toss.config.ts`일 수 있으나, 실제 CLI가 생성한 파일과 현재 공식 템플릿을 기준으로 한다.
- `@apps-in-toss/web-framework` 버전을 임의로 고정하거나 최신이라고 주장하지 않는다. 설치 시점의 안정 버전과 호환성을 확인하고 lock 파일에 고정한다.

- `appName` 후보 `sizenote`는 콘솔 중복·등록 규칙·브랜드 검토 전까지 확정값으로 취급하지 않는다.

# 2. 제품 범위 — MVP와 제외 범위

## 2.1 MVP에서 구현할 기능

### A. 내 공간 관리

- 기본 공간 그룹: 주방, 거실, 침실, 세탁실, 욕실, 현관, 베란다, 기타
- 공간 추가·이름 변경·삭제
- 공간별 메모
- 공간별 측정 대상 목록
- 공간/측정 대상의 최근 수정일 표시
- 삭제 전 확인 및 관련 비교 이력 처리 정책

### B. 측정 대상 관리

- 측정 대상 추가·수정·삭제
- 기본 측정 대상 템플릿 제공
- 직접 이름을 입력해 사용자 지정 측정 대상 생성
- 치수 입력: 가로(width), 깊이(depth), 높이(height)
- 선택 치수: 문 유효 폭, 문 유효 높이, 통로 폭, 통로 높이, 좌우 여유, 후면 여유, 상단 여유, 문 개방 공간, 서랍 인출 공간
- 필요한 치수만 사용하도록 선택 입력 지원
- 단위: 내부 저장은 정수 mm를 권장하고, 화면은 cm 기본 표시
- mm ↔ cm 변환 및 반올림 규칙을 공통 유틸리티로 구현
- 치수별 메모 및 측정일
- 출처 구분: 직접 측정 / 도면 참고 / 제조사 문서 / 기타 참고 / 미확인
- 사용자가 직접 입력한 값과 추정·참고 값을 UI에서 구분

### C. 카메라 촬영·사진 메모 및 보조 측정

- 측정 대상에 사진을 최대 3장까지 연결한다. 측정 전체를 설명하는 대표 사진 1장과 상세 사진을 구분할 수 있다.
- 카메라 촬영은 앱인토스 공식 Device API의 `openCamera`, 앨범 선택은 `fetchAlbumPhotos` 등 현재 SDK에서 확인된 API를 사용한다. 실제 import 경로·인자·반환 타입은 설치된 SDK 타입과 공식 예제를 확인하고 추측하지 않는다.
- 카메라/앨범 API가 제공하는 권한 동의 흐름을 사용한다. SDK가 동일 기능을 제공하는 경우 `input[type=file]`, `getUserMedia` 등으로 우회하지 않는다.
- 카메라·앨범 권한은 사용자가 촬영/사진 추가를 누른 시점에만 설명하고 요청한다.
- 촬영한 사진은 원본과 축소본의 저장 정책을 분리하고, 실제 앱 재진입 후에도 불러올 수 있는지 검증한다.
- Base64 원본을 핵심 상태 JSON에 넣지 않는다. 사진 바이너리 저장, 크기 제한, 압축, 파일 참조 방식은 SDK 공식 API와 POC로 확인한다.
- 사진 저장이 불가능하거나 실패하면 사진이 저장된 것처럼 보이지 않게 하고, 치수·메모 수동 저장은 계속 가능해야 한다.

#### C-1. 사진 기반 보조 측정 — MVP POC 대상

- 사진에서 치수를 자동으로 추정하는 AI가 아니라, 사용자가 사진 위에 측정 기준점과 기준 길이를 지정하는 **수동 보정형 사진 측정**을 우선 구현한다.
- 흐름: 촬영/앨범 선택 → 사진 확인 및 회전/자르기(필요 시) → 기준 길이 지정 → 측정할 두 점 지정 → 계산된 참고 치수 확인 → 사용자가 수정/확정 → 측정 기록 저장.
- 기준 길이는 같은 평면에 놓인 줄자 눈금, 길이를 알고 있는 자, A4 용지의 한 변 등 실제 길이를 사용자가 확인할 수 있는 물체로 보정한다. A4 규격은 실제 용지 크기와 촬영 상태를 사용자가 확인한 경우에만 기준으로 허용한다.
- 기준선과 측정선은 가능한 한 같은 평면·같은 깊이에 있어야 한다. 서로 다른 깊이, 기울어진 촬영, 광각 렌즈 왜곡, 곡면, 가려진 경계는 측정 오차가 커질 수 있으므로 경고한다.
- 초기 구현에서는 사용자가 기준선 양 끝을 직접 터치하고 실제 길이(mm)를 입력한 뒤 측정 대상의 두 점을 터치하는 1차원 보정 방식을 우선한다.
- 보정된 픽셀/mm 비율로 길이를 계산하되 사진의 원근 왜곡을 자동 해결했다고 표시하지 않는다. 필요하면 향후 동일 평면의 사각 기준물 4점을 지정하는 원근 보정(호모그래피)을 별도 POC로 검토한다.
- 계산값은 `사진 보조 측정`으로 저장하고 `직접 측정`과 시각적으로 구분한다. 사용자가 줄자 등으로 확인해 수정한 값은 `직접 확인/보정` 상태로 남긴다.
- 측정 결과에는 사용한 기준물·기준 길이·기준점·사진 ID·보정 방법·측정 시각·사용자 수정 여부를 저장한다.
- 사진 보조 측정값은 참고값이며 실제 설치 판단 전 줄자/레이저 거리측정기 등으로 재확인하도록 안내한다.
- 방의 전체 깊이, 가려진 후면, 입체 공간의 높이/폭, 복잡한 반입 경로를 단일 사진으로 측정했다고 주장하지 않는다.
- 기준 길이를 지정할 수 없거나 사진 품질이 낮으면 자동 숫자를 내지 말고 `사진 기록만 저장` 또는 `직접 입력`으로 전환한다.

#### C-2. AR/Depth 자동 측정 — 별도 기술 검증, MVP 기본 제외

- ARKit, ARCore Depth, LiDAR/ToF를 통한 실시간 AR 측정은 네이티브 플랫폼 기능과 기기 지원에 의존한다.
- 앱인토스 WebView 및 현행 SDK가 AR 세션·평면 추적·깊이 맵·실측 좌표를 공식 지원하는지 먼저 확인한다. 카메라 촬영 API가 있다는 사실만으로 AR 측정도 지원한다고 간주하지 않는다.
- Android ARCore Depth는 지원 기기 여부 확인과 별도 활성화가 필요하며 모든 기기에서 동일하게 지원된다고 가정하지 않는다.
- iOS/Android 양쪽에서 동일한 UX를 제공할 수 있는 공식적이고 정책상 허용된 경로가 검증되지 않으면 구현하지 않는다. 임의 네이티브 브릿지, 숨겨진 WebView API, 비공식 플러그인으로 우회하지 않는다.
- 검증 결과가 불가능하거나 앱인토스 범위를 벗어나면 기능을 제외하고 사진 보조 측정 및 수동 입력을 대안으로 유지한다.

### D. 제품 정보 관리

- 제품명
- 카테고리: 냉장고, 세탁기, 건조기, 식기세척기, TV, 침대, 소파, 책상, 옷장, 커튼, 기타
- 제조사 및 모델명(선택)
- 제품 외형 치수: 가로·깊이·높이
- 포장 상태 치수(선택)
- 제조사 권장 설치 여유: 좌·우·후면·상단 등 필요한 방향별 입력
- 문/서랍 개방에 필요한 추가 공간(선택)
- 설치 관련 주의사항 메모
- 치수 출처: 제품 설명서 / 제조사 공식 페이지에서 사용자 확인 / 판매 페이지 / 직접 측정 / 기타
- 출처 URL은 참고용으로만 저장할 수 있으며 MVP 핵심 기능은 외부 페이지를 열지 않고도 동작해야 한다.
- 외부 제품 DB, 크롤링, 쇼핑몰 API, 최저가 API를 사용하지 않는다.
- 사용자가 입력하지 않은 제조사 제원이나 여유 공간을 임의로 만들어내지 않는다.

### E. 제품과 공간 비교

- 사용자가 저장한 공간 하나와 제품 하나를 선택해 비교한다.
- 모든 치수의 방향과 의미를 사용자에게 명확히 보여 준다.
- 필요한 공간 크기와 제품 크기를 방향별로 비교한다.
- 설치 여유가 필요한 방향은 제품 크기에 필요한 여유 공간을 더해 계산한다.
- 계산에 필요한 값이 누락되면 결과를 `추가 확인 필요`로 처리한다.
- 제품 크기가 공간보다 큰 경우 `규격 초과`로 처리한다.
- 입력된 조건을 모두 통과한 경우에도 `입력값 기준 규격 충족`으로만 표현한다. 실제 설치 가능을 보증하지 않는다.
- 제조사 권장 여유가 미입력인데 임의의 표준 여유를 추가하지 않는다.
- 결과에 사용한 공간 측정값·제품 값·판정 시각을 스냅샷으로 저장한다.
- 공간 또는 제품 정보가 변경된 후 과거 비교 결과가 자동으로 바뀌지 않도록 한다. 재비교 기능을 별도로 제공한다.

### F. 반입 경로 사전 점검 — 단순 선별 수준

MVP에서 반입 경로 기능은 설치 공간 판정과 구분한다.

- 경로 구간: 공동현관, 엘리베이터, 복도, 현관문, 방문, 계단, 기타
- 구간별 통과 폭·통과 높이·내부 깊이 입력
- 사용자는 제품 외형 또는 포장 외형 중 비교할 기준을 선택
- 좁은 구간의 치수와 제품의 선택한 방향 치수를 단순 비교
- 방향 회전·기울이기·코너 회전·계단 이동을 정밀하게 계산하지 않는다.
- 제품을 회전하면 통과할 수 있는지 단순 폭·높이 비교만으로 판정하지 않는다.
- 회전이나 기울이기가 필요하거나 경로 형상이 복잡하면 `현장 확인 필요`로 표시한다.
- 반입 경로 결과는 `통과 규격 충족(단순 비교)` 또는 `추가 확인 필요`로만 제공한다.
- 실제 배송·설치 기사 또는 제품 공급업체의 현장 확인을 대체하지 않는다.

### G. 비교 이력

- 최근 비교 이력 최대 20개를 기본값으로 검토한다.
- 비교 날짜, 제품명, 공간명, 판정 결과 표시
- 이력 상세에서 당시 스냅샷 조회
- 비교 결과 삭제
- 전체 데이터 초기화
- 최근 이력 상한은 실제 Storage 용량 POC를 통해 조정한다.

## 2.2 MVP에서 제외할 기능 및 별도 검증 항목

- ARKit·ARCore·LiDAR 기반 실시간 자동 측정(앱인토스 WebView에서 공식 지원 및 양 플랫폼 검증 전까지 제외)
- 사진만으로 실제 치수를 자동 추정하는 AI·클라우드 이미지 분석
- 3D 인테리어·가상 가구 배치
- 복잡한 3D 물체 회전·코너 통과 시뮬레이션
- 도면 자동 인식 및 CAD 파일 파싱
- 쇼핑몰 상품 자동 검색 및 제품 DB
- 바코드·모델명 자동 제원 조회
- 가격 비교·구매 연결·제휴 링크
- 회원가입, 자체 로그인, 소셜 로그인
- 토스 로그인 및 사용자 식별키 수집
- 자체 백엔드, Supabase, Firebase, 외부 DB
- 가족 공유·클라우드 동기화
- 푸시 알림·예약 알림
- 광고·구독·인앱 결제
- 외부 웹사이트를 주요 흐름으로 사용하는 구조

사진 보조 측정은 C-1의 제한된 수동 보정 방식만 MVP POC 대상으로 삼는다. AR 자동 측정은 별도 기술 검증을 통과하기 전까지 로드맵 항목이다. 추가 기능은 핵심 저장·비교 흐름을 안정화한 뒤 우선순위를 검토한다.

# 3. UX 및 화면 설계

## 3.1 전체 UX 원칙

- 앱에 진입하면 즉시 홈 화면에서 핵심 행동을 보여 준다.
- 첫 진입 시 로그인·권한 요청·광고·알림 동의·바텀시트를 자동으로 띄우지 않는다.
- 자체 탭바는 MVP에서 만들지 않는 것을 우선한다. 필요성이 확인된 경우 앱인토스의 플로팅 탭바 공식 가이드를 확인한다.
- 앱인토스 기본 내비게이션을 존중하고 자체 상단 닫기·뒤로가기 버튼을 중복 구현하지 않는다.
- 터치 영역은 충분히 크게 확보한다.
- 가로 스크롤에 의존하지 않는다.
- 숫자와 단위를 붙여 읽기 쉽게 배치한다.
- 빈 화면, 데이터 없음, 로딩, 저장 실패, 권한 거부, 사진 미지원 상태를 모두 설계한다.
- 모든 파괴적 동작(삭제·초기화)은 확인 절차를 둔다.
- 사용자가 입력 중 화면을 이탈하거나 저장에 실패해도 복구할 수 있도록 입력 상태를 관리한다.

## 3.2 권장 화면 목록

### 화면 1. 홈

구성:

- 상단 브랜드명 `사이즈노트`
- 헤드라인 `사기 전에, 우리 집에 맞는지.`
- 주요 CTA `제품 크기 비교하기`
- 공간 요약 카드: 주방·거실·침실·세탁실 등
- 최근 등록한 측정 항목
- 최근 제품 비교 기록
- 첫 사용자에게는 `우리 집 공간 등록하기` CTA

홈에서 기능 설명을 길게 노출하지 않는다. 등록된 공간이 없으면 빈 상태와 첫 등록 CTA를 명확하게 보여 준다.

### 화면 2. 공간 목록

- 공간 그룹 카드 또는 간결한 목록
- 공간명
- 등록된 측정 항목 수
- 최근 업데이트 날짜
- 공간 추가 버튼

### 화면 3. 공간 상세

- 공간명 및 메모
- 측정 항목 목록
- 항목별 대표 치수
- 사진이 있으면 썸네일
- 측정 출처 및 측정일
- 측정 항목 추가·수정·삭제

### 화면 4. 측정 항목 등록/수정

입력 필드:

- 측정 대상명
- 측정 대상 유형
- 가로(mm 또는 cm)
- 깊이(mm 또는 cm)
- 높이(mm 또는 cm)
- 추가 측정 항목(선택)
- 측정 출처
- 측정 날짜(기본 현재 날짜)
- 측정 방식 선택: 직접 입력 / 사진 보조 측정
- 사진 첨부 및 사진 위 기준선·측정점 지정(사진 POC 통과 시)
- 계산된 사진 참고값 확인 및 직접 수정
- 메모

필수로 모든 3개 치수를 입력하도록 강제하지 않는다. 측정 대상에 필요한 값만 선택적으로 입력할 수 있어야 한다. 다만 비교에 필요한 필드가 없으면 비교 결과에 누락 항목을 표시한다.

### 화면 5. 제품 등록/수정

- 제품명
- 카테고리
- 제조사·모델명(선택)
- 제품 가로·깊이·높이
- 포장 치수(선택)
- 방향별 설치 여유(선택)
- 문/서랍 개방 조건(선택)
- 제원 출처
- 메모

### 화면 6. 제품 비교

- 제품 선택
- 비교할 공간 및 측정 항목 선택
- 필요한 설치 여유 확인
- 비교 실행 CTA
- 누락된 값 안내

### 화면 7. 비교 결과

- 결과 상태: 규격 충족 / 규격 초과 / 추가 확인 필요
- 방향별 공간·제품 치수 대조
- 필요한 설치 여유 계산
- 미입력·미확인 조건 목록
- 반입 경로 확인 결과(입력된 경우)
- `비교 기록 저장` 및 `다른 제품 비교` CTA
- 주의 문구: 입력된 값에 근거한 참고 결과이며 실제 설치를 보증하지 않음

### 화면 8. 비교 이력

- 최근 비교 목록
- 제품명·공간명·비교일
- 판정 상태
- 상세에서 과거 스냅샷 표시

### 화면 9. 설정 및 데이터 관리

- 앱 정보
- 데이터 저장 위치 및 기기 변경 시 유의사항
- 사진 저장 상태 안내
- 전체 데이터 내보내기/복원은 MVP 범위와 Storage 제한 확인 후 결정
- 모든 데이터 삭제
- 개인정보 및 이용 안내

### 화면 10. 사진 보조 측정

- 촬영/앨범에서 사진 가져오기
- 기준 길이 안내 및 기준선 두 점 지정
- 기준물 실제 길이 입력(cm/mm)
- 측정할 대상의 시작점과 끝점 지정
- 계산된 참고 치수와 보정값 표시
- `다시 지정`, `직접 입력으로 수정`, `측정값 저장` 제공
- 측정 평면이 다르거나 원근 왜곡이 큰 경우 경고 및 참고값 처리
- 사진에서 확인할 수 없는 깊이·후면·가려진 치수는 추가 확인 필요로 표시

### 화면 11. 제품 후보 비교

- 저장한 동일 공간/측정 항목에 제품 후보 최대 3개를 선택
- 가로·깊이·높이 및 설치 여유를 같은 기준으로 나란히 표시
- 각 후보의 FIT / OVER / REVIEW를 표시하고 판정 근거를 확인
- 제품 정보는 사용자가 직접 등록한 값만 사용
- 후보 간 최저가나 구매 링크를 임의로 제공하지 않음

### 화면 12. 측정 가이드 및 데이터 백업

- 공간 유형·측정 대상별 필수/권장 측정 항목 체크리스트
- 가로·깊이·높이 및 문/통로 측정 방법을 간단한 선형 안내도로 표시
- 측정값의 출처, 측정일, 사진 보조 측정 여부를 확인
- 오래되었거나 신뢰 수준이 낮은 치수는 비교 전에 재측정 권고
- 데이터 내보내기/가져오기는 앱인토스 File API 및 실제 토스 앱에서 검증된 경우에만 제공
- 백업 파일에는 개인정보가 포함될 수 있음을 안내하고 사용자 동작으로만 생성/복원

## 3.3 UX 카피 예시

좋은 표현:

- `우리 집에 맞는지 미리 확인해 보세요.`
- `가로와 깊이를 입력해 주세요.`
- `직접 잰 치수인가요?`
- `사진에 기준 길이를 표시하면 참고 치수를 계산할 수 있어요.`
- `기준물과 측정할 부분이 같은 평면에 있는지 확인해 주세요.`
- `사진으로 계산한 값은 줄자로 한 번 더 확인해 주세요.`
- `제품 설명서에 적힌 설치 간격을 입력해 주세요.`
- `입력한 공간 치수보다 제품이 커요.`
- `필요한 치수가 없어 결과를 확정할 수 없어요.`
- `제품 설명서의 설치 조건도 확인해 주세요.`

피해야 할 표현:

- `무조건 설치 가능`
- `100% 들어갑니다`
- `AI가 정확히 측정했어요` (실제 AI 측정 기능이 없음)
- `자동으로 모든 설치 조건을 확인했어요`
- `구매해도 안전해요`

# 4. 디자인 시스템 및 브랜딩

## 4.1 디자인 방향

- 밝고 차분한 생활 기록 도구. 미니멀한 북유럽/재팬디 인테리어 감성의 웜 우드 톤을 적용한다.
- 배경은 아이보리·크림·웜 베이지, 표면은 깨끗한 오프화이트, 텍스트는 짙은 웜 차콜로 구성한다.
- 주요 액션은 내추럴 우드 브라운, 보조색은 세이지 그린, 경고색은 머스터드/테라코타를 상태에만 제한적으로 사용한다.
- 우드 질감은 화면 배경 전체에 반복하지 않는다. 온보딩/빈 상태의 작은 가구 일러스트나 얇은 포인트에만 사용한다.
- 둥근 카드와 아주 절제된 그림자, 얇은 웜그레이 구분선을 사용한다.
- 정보 밀도를 낮추고 치수 숫자와 단위를 강조한다.
- 과도한 3D 일러스트, 진한 나무결 텍스처, 가죽 질감, 그라디언트 남용, 장식용 그래픽을 금지한다.
- 화면마다 서로 다른 디자인을 적용하지 말고 동일한 디자인 토큰 사용
- 토스 TDS 사용 시 현재 React 패키지·컴포넌트·라이선스·앱인토스 적용 범위를 먼저 확인

# 5. 측정과 비교의 도메인 로직

## 5.1 단위 규칙

- 내부 저장 단위는 정수 mm를 권장한다.
- 화면의 기본 표시 단위는 cm로 한다.
- `1 cm = 10 mm` 변환은 하나의 공통 유틸리티에서 처리한다.
- 소수점이 있는 cm 값은 mm로 변환할 때 반올림 규칙을 일관되게 적용한다.
- 입력값은 양수이며 도메인별 합리적 상한을 검증한다.
- 0, 음수, NaN, Infinity, 비정상적으로 큰 값은 저장하지 않는다.
- 입력 필드의 `cm` / `mm` 단위 표시를 항상 명확히 한다.

## 5.2 치수 의미 정의

`width`, `depth`, `height`는 측정 대상의 사용자가 지정한 기준 방향을 뜻한다. 모든 제품과 공간이 동일한 방향으로 측정됐다고 자동 가정하지 않는다.

UI에서 다음 기준을 안내한다.

- 가로: 정면에서 봤을 때 좌우
- 깊이: 정면에서 뒤쪽 방향
- 높이: 바닥에서 위쪽

공간 측정값은 벽·걸레받이·문틀·배관·손잡이 등 실제 사용 가능한 범위를 기준으로 측정하도록 안내한다. 방 전체 크기와 실제 제품 설치 가능 공간을 혼동하지 않도록 한다.

## 5.3 비교 함수의 기본 개념

단순 외형 치수 비교:

```ts
function compareDimension(spaceMm: number, productMm: number) {
  return {
    fits: productMm <= spaceMm,
    remainingMm: spaceMm - productMm,
  };
}
```

설치 여유 포함 비교:

```ts
function requiredDimension(
  productMm: number,
  beforeClearanceMm: number,
  afterClearanceMm: number
) {
  return productMm + beforeClearanceMm + afterClearanceMm;
}
```

실제 구현은 위 예시보다 더 엄격하게 검증한다.

- 입력값 중 하나라도 미확인·누락이면 해당 방향을 `UNKNOWN`으로 처리한다.
- 설치 여유가 필요한데 값이 없으면 자동으로 0을 넣지 않는다. 해당 여유가 불필요하다고 사용자가 확인했을 때만 0을 허용한다.
- 제품의 방향과 공간의 방향이 일치하는지 사용자가 확인할 수 있어야 한다.
- 제품의 가로·깊이 방향을 바꿔 비교하는 기능을 제공한다면 두 방향을 바꿔서 계산한 결과임을 명확히 표시하고, 문 개방·환기·배관 등 비대칭 설치 조건을 자동으로 해결했다고 표현하지 않는다.
- `규격 충족`은 필수 입력된 모든 단순 치수 조건을 통과했다는 뜻으로 제한한다.
- 설치 조건이 누락되거나 실제 현장 조건이 미확인인 경우 전체 결과는 `추가 확인 필요`를 우선한다.

## 5.4 전체 판정 정책

`FIT` / `OVER` / `REVIEW` 세 상태를 사용한다.

- `OVER`: 확실히 입력된 필수 공간 치수보다 제품 요구 치수가 큼
- `FIT`: 판정에 필요한 모든 필수 치수와 설치 여유가 확인됐고, 단순 비교 조건을 모두 통과함
- `REVIEW`: 필수 치수 누락, 제조사 설치 여유 미확인, 방향 불명확, 문 개방·배관·회전·코너 등 현장 확인이 필요한 조건 존재

우선순위는 `OVER`보다 `REVIEW`를 무조건 우선하는 것이 아니다. 예를 들어 필수 폭을 초과하는 값이 확정되어 있으면 `OVER`로 표시하고, 그 외에도 미확인 조건이 있음을 별도 목록으로 보여 준다. 필수 치수 초과가 없고 미확인 조건이 있다면 `REVIEW`로 표시한다.

판정 결과에는 언제나 다음 메타데이터를 포함한다.

- 비교한 공간과 측정 항목
- 비교한 제품
- 사용한 치수
- 출처 및 측정일
- 계산 시각
- 미확인 조건
- 판정 알고리즘 버전

## 5.5 반입 경로 로직의 제한

MVP는 실제 3차원 물체 이동을 계산하지 않는다.

- 문 폭과 제품 폭 비교만으로 회전 반입을 보장하지 않는다.
- 복도 코너, 계단참, 문틀 두께, 손잡이, 포장 모서리, 기울이기 등은 단순 계산으로 판정하지 않는다.
- 측정 경로가 직선이 아니거나 회전이 필요하면 항상 `현장 확인 필요`를 표시한다.
- 포장 외형과 제품 본체 외형은 별도 값으로 취급한다.
- 입력되지 않은 포장 크기를 제품 본체 크기로 대체하지 않는다.

# 8. 기술 아키텍처

## 8.1 기본 스택

- 앱 형태: 앱인토스 비게임 WebView 미니앱
- 프론트엔드: React + TypeScript strict
- 개발 서버/번들: Vite 및 현재 공식 앱인토스 CLI
- SDK: `@apps-in-toss/web-framework`의 현재 공식 호환 버전
- 저장: 앱인토스 `Storage` API
- 사진: 공식 `Device` / `File` API 지원 범위 확인 후 선택 적용
- 테스트: 프로젝트 템플릿과 호환되는 Vitest 또는 공식 권장 테스트 도구
- UI: 가벼운 CSS 및 TDS 적용 검토

독립형 React Native, Expo, 네이티브 앱으로 구현하지 않는다.

## 8.2 Repository / Adapter 분리

도메인 로직은 Toss SDK에 직접 의존하지 않도록 한다.

예시:

```ts
export interface KeyValueStorage {
  get(key: string): Promise<string | null>;
  set(key: string, value: string): Promise<void>;
  remove(key: string): Promise<void>;
}
```

- `TossStorageAdapter`: 앱인토스 공식 Storage SDK 구현
- `BrowserStorageAdapter`: 로컬 브라우저 개발·테스트 전용
- 실제 운영 환경에서 `localStorage`를 기본 저장소로 사용하지 않는다.
- SDK API import와 인자 형식은 현재 설치 패키지 타입을 확인한다.
- 브라우저 Preview에서만 동작하는 기능을 토스 운영 환경에서 동작한다고 보고하지 않는다.

## 8.3 데이터 저장 전략

- 별도 서버 없이 로컬 저장을 기본으로 한다.
- 사용자 위치, 상세 주소, 사진, 공간 치수 데이터를 외부 서버로 전송하지 않는다.
- 앱을 삭제하거나 기기를 변경할 때 데이터가 유지된다고 보장하지 않는다.
- 첫 저장 전 사용자에게 데이터가 기기 환경에 종속될 수 있음을 짧게 알린다.
- 앱 전용 Storage 키만 읽고 쓴다.
- 전체 Storage 초기화 API를 무분별하게 호출하지 않는다.
- JSON 파싱 실패 시 앱을 중단하지 말고 복구·초기화 안내를 제공한다.
- 모든 저장 동작은 실패 상태를 UI에 전달한다.

## 8.4 사진 POC

사진을 출시 기능으로 넣기 전에 아래 POC를 완료한다.

1. 토스 iOS에서 카메라 또는 앨범 기능 호출이 가능한지 확인한다.
2. 토스 Android에서 동일한 기능을 확인한다.
3. 반환 객체의 URI/Base64/파일 식별 방식과 수명 확인.
4. 사진을 앱 전용 저장소에 저장할 수 있는지 확인.
5. 앱을 완전히 종료한 뒤 다시 진입해도 사진이 표시되는지 확인.
6. 사진 1장 및 여러 장 저장 시 용량과 실패 조건 측정.
7. 이미지 축소·압축을 적용할 수 있는지 대상 WebView에서 확인.
8. 저장·불러오기·삭제 테스트를 수행.
9. 테스트 결과와 제한을 `docs/PHOTO_POC.md`에 기록.

POC를 통과하지 못하면 사진 기능은 출시 MVP에서 숨기고 치수·텍스트 중심 기능을 제공한다.

## 8.5 사진 보조 측정 기술 구조

- 앱인토스 `openCamera` / `fetchAlbumPhotos`의 현재 SDK API를 통해 촬영/앨범 이미지를 얻는다. 공식 예제는 `base64: true` 방식과 `data:image/jpeg;base64,` 프리픽스 사용을 안내하므로 현재 반환 타입과 MIME 정보를 확인해 적용한다.
- 권한 설정은 실제 사용하는 `camera` 및 `photos` 권한만 앱 설정에 선언한다. 카메라와 앨범 권한을 한꺼번에 요청하지 않고 사용 시점에 필요한 것만 요청한다.
- 이미지 표시·회전·크롭·기준점 선택·측정선 그리기는 WebView의 이미지 표시 및 2D 오버레이로 구현할 수 있는지 POC한다. 측정점 좌표는 원본 픽셀 좌표와 화면 표시 좌표를 변환해 저장한다.
- 1차 POC는 동일 평면 내 기준선 하나의 알려진 길이로 픽셀/mm 비율을 계산한다. `실제 길이(mm) / 픽셀 거리 = mm per pixel` 관계를 사용하고, 길이는 정수 mm로 저장한다.
- 캘리브레이션 선과 측정 선의 평면/깊이가 다르면 오차가 발생한다. 사진 촬영 안내에서 카메라를 측정면에 정면으로 두고 기준물과 대상이 같은 면에 놓이도록 유도한다.
- 이미지 편집 UI의 확대/이동(핀치 줌 등)은 측정점 정밀 선택에만 사용한다. 실제 기기에서 터치 좌표 변환 정확도를 테스트한다.
- 기준 길이 보정과 측정점 지정 기록을 함께 보관해 추후 재조정할 수 있도록 한다.
- 사진 파일은 별도 사진 저장소 어댑터로 관리하고, 메타데이터 JSON에는 사진 ID/저장 키만 둔다. 저장 방식은 SDK Storage/File의 실제 지원과 용량 제한을 확인한 뒤 선택한다.
- 썸네일을 만들 수 있으면 UI 목록에는 썸네일을 사용하고 원본은 상세 화면에서만 불러온다. 원본 보존 정책과 압축 품질은 실제 기기 POC 후 결정한다.
- 브라우저용 `BrowserStorageAdapter`/Mock Camera는 로컬 개발 테스트용이다. 운영 토스 앱에서 정상 저장된다는 근거로 취급하지 않는다.
- 측정 엔진은 UI와 분리한 순수 함수로 구성한다. 수식/좌표변환/잘못된 점 선택/0에 가까운 기준선/비정상 길이/이미지 회전/크롭을 단위 테스트한다.
- 4개 코너를 이용한 원근 보정은 별도 옵션으로 POC하되 MVP 1차에서는 억지로 구현하지 않는다. 알고리즘을 정확히 검증하지 못하면 기능을 노출하지 않는다.

## 8.6 유용성 개선 기능의 범위

- **측정 체크리스트:** 공간 및 대상 유형별로 어떤 치수를 재야 하는지 보여 준다. 체크리스트는 사용자 안내용이며 자동 판정을 대신하지 않는다.
- **측정값 재사용:** 저장된 측정 항목을 복제해 유사한 공간/대상에 재사용하고, 수정 이력을 남긴다.
- **제품 후보 나란히 비교:** 사용자가 입력한 후보 최대 3개를 동일 공간 기준으로 비교한다.
- **측정 최신성 표시:** 측정일이 오래됐거나 출처가 미확인인 값은 상태 라벨과 재측정 안내를 표시한다. 임의의 만료일로 데이터를 삭제하지 않는다.
- **측정 보고서:** 선택된 사진·치수·출처·메모·판정 결과를 한 화면에서 확인하고, 파일 내보내기는 공식 File API 및 실기기 검증 통과 시에만 제공한다.
- **수동 백업/복원:** 데이터 이동/복구를 제공할 수 있는지 SDK File API와 정책을 확인한다. 미검증이면 설정에 기능을 만들지 않고 제한을 안내한다.

- 저장 데이터 크기 제한·백업·복구 가능성은 확인된 내용만 안내한다.

# 15. 작업 단계와 구현 순서

각 단계를 완료할 때 테스트 결과와 미완료 항목을 보고한다. 작업 중 사용자 승인 없이 Git commit, push, 콘솔 업로드, 앱 등록, 출시를 수행하지 않는다.

## Phase 0 — 저장소 및 SDK 검증

- 저장소 확인
- 공식 문서 확인
- SDK 버전·템플릿 확인
- 현재 빌드·테스트 명령 파악
- 프로젝트 생성 또는 기존 프로젝트 재사용 결정
- `docs/TOSS_SDK_COMPATIBILITY.md` 작성
- 아직 알 수 없는 부분을 목록화

## Phase 1 — 앱 셸 및 디자인 시스템

- 앱 진입 및 기본 레이아웃
- 홈·공간 목록·측정 상세 화면 이동
- 디자인 토큰
- 공통 버튼·카드·필드·상태 배지
- Safe Area 및 키보드 확인
- 반응형 작은 화면 레이아웃

## Phase 2 — 공간 및 측정 데이터

- 공간 CRUD
- 측정 대상 CRUD
- mm 저장 및 cm 표시
- 입력 검증
- 출처·측정일 관리
- Toss Storage Adapter
- Browser Storage Adapter
- 스키마 버전 및 마이그레이션

## Phase 3 — 제품 정보 및 비교 엔진

- 제품 CRUD
- 설치 여유 입력
- 비교 규칙 순수 함수
- FIT / OVER / REVIEW 분류
- 판정 근거 표시
- 비교 결과 스냅샷 저장
- 과거 결과 불변성 테스트

## Phase 4 — 반입 경로 기초 기능

- 통과 구간 등록
- 구간별 치수 입력
- 단순 비교
- 회전·코너·계단 등 미지원 조건 REVIEW 처리
- 설치 공간 결과와 별도 표시

## Phase 5 — 카메라·사진 저장 및 보조 측정 POC

- 공식 `openCamera` / `fetchAlbumPhotos` API와 권한 선언 확인
- 사진의 Base64/URI 반환 형태 및 MIME 타입 확인
- 사진 압축·썸네일·저장 용량·재진입 지속성 검증
- 기준 길이 1개를 이용한 1차원 사진 보정 측정 POC
- 사진 회전/크롭/줌에 따른 포인트 좌표 정합성 테스트
- iOS·Android 토스 앱에서 촬영·저장·불러오기·삭제 테스트
- 오차 측정: 줄자/레이저 측정기와 비교한 오차 분포를 기록하고 허용 가능한 사용 범위를 정한다.
- 검증을 통과한 항목만 제한적으로 출시한다. 오차가 크거나 저장이 불안정하면 사진 메모만 제공하고 계산 기능은 비활성화한다.
- ARKit/ARCore Depth는 WebView/SDK 공식 지원, 권한, 플랫폼 동등성, 배포 정책을 별도 조사하고 MVP와 분리한다.

## Phase 6 — 제품 후보·측정 가이드 및 데이터 품질

- 측정 대상별 체크리스트
- 동일 공간에 대한 제품 후보 최대 3개 비교
- 측정값 출처/신뢰 수준/최근 측정일 표시
- 측정값 복제 및 재사용
- 데이터 백업/복원은 SDK 지원 및 실기기 검증 시에만 적용

## Phase 7 — 안정화와 출시 준비

- 전체 테스트
- 빌드 및 정적 검사
- 실제 토스 앱 테스트 체크리스트
- UI/UX 정책 검토
- 개인정보·저장 안내
- 브랜드 아이콘 및 앱 정보 에셋
- 비게임 출시 체크리스트
- 미완료 및 검증 불가 항목 보고

# 16. 완료 정의 (Definition of Done)

다음 조건을 충족해야 MVP 완료로 보고한다.

- [ ] 앱인토스 WebView 프로젝트로 실행된다.
- [ ] 현재 공식 SDK 및 CLI 구조를 사용한다.
- [ ] 홈 화면에서 빈 상태와 기존 데이터 상태가 정상 표시된다.
- [ ] 공간을 생성·수정·삭제할 수 있다.
- [ ] 측정 항목을 생성·수정·삭제할 수 있다.
- [ ] 측정값을 mm 정수로 안전하게 저장하고 cm로 표시한다.
- [ ] 측정 출처와 날짜를 구분한다.
- [ ] 제품 정보를 생성·수정·삭제할 수 있다.
- [ ] 공간과 제품을 비교할 수 있다.
- [ ] FIT / OVER / REVIEW 결과가 규칙에 맞게 나온다.
- [ ] 설치 여유 미확인 값을 임의로 0 처리하지 않는다.
- [ ] 과거 비교 결과가 스냅샷으로 유지된다.
- [ ] 반입 경로의 복잡한 3D 판정을 하는 것처럼 과장하지 않는다.
- [ ] Storage 저장 실패와 데이터 손상에 대응한다.
- [ ] 사진이 검증되지 않았으면 저장된다고 표시하지 않는다.
- [ ] 사진 보조 측정은 기준 길이와 기준점을 사용하며 참고값으로 표시한다.
- [ ] 사진 보조 측정의 오차와 제한을 실기기에서 검증하고 사용자에게 안내한다.
- [ ] 사진의 기준점/측정점 좌표가 회전·크롭·확대 상태에서도 정확히 변환된다.
- [ ] 측정값에 입력 방식·출처·측정일·신뢰 수준이 보존된다.
- [ ] 제품 후보 최대 3개 비교와 측정 체크리스트가 동작한다.
- [ ] AR 자동 측정은 공식 지원을 확인하지 않은 상태에서 구현 완료로 표시하지 않는다.
- [ ] 사용자 공간 데이터가 외부로 전송되지 않는다.
- [ ] 단위 테스트가 통과한다.
- [ ] 빌드가 성공한다.
- [ ] 앱인토스 정책 체크리스트를 검토한다.
- [ ] 실제 토스 앱에서 검증한 항목과 미검증 항목이 구분된다.
- [ ] README와 docs가 현재 구현 상태와 일치한다.

# 17. Claude Code 실행 지시

이 문서를 받은 직후 모든 코드를 한 번에 덮어쓰지 말고 아래 방식으로 진행한다.

1. 현재 저장소를 조사하고 기존 변경사항을 보존한다.
2. 앱인토스 공식 문서를 확인하고 현재 SDK 설정을 파악한다.
3. 구현 가능한 기능과 공식 확인이 필요한 기능을 구분한다.
4. MVP 화면과 데이터 모델을 먼저 정리한다.
5. 사용자에게 질문하지 않아도 되는 디자인·구조 결정은 합리적으로 판단해 진행한다.
6. 다만 앱인토스 콘솔의 앱 식별자, 파트너 권한, 실제 기기 테스트처럼 사용자가 제공해야 하는 정보가 없으면 임의 생성하지 말고 필요한 부분만 명확히 표시한다.
7. Phase 순서대로 실제 코드를 작성하고 각 단계마다 빌드·테스트한다.
8. 샘플 데이터는 개발·미리보기 전용으로 분리하고 실사용 데이터처럼 보이지 않게 한다.
9. 핵심 계산 로직은 React 컴포넌트와 분리해 순수 함수로 구현한다.
10. 실제 SDK 타입과 다른 가짜 API, 임의 브릿지, 브라우저 API 우회를 만들지 않는다.
11. 구현하지 않은 기능은 비활성화하거나 미지원으로 표시한다.
12. 사용자 승인 없이 커밋·푸시·배포·콘솔 업로드·출시하지 않는다.

# 18. 추가 구현 원칙 — 사진 측정 신뢰성 및 기능 우선순위

## 18.1 측정 결과 신뢰 수준

모든 치수는 숫자만 저장하지 말고 측정 방식과 출처를 함께 표시한다.

| 구분 | 의미 | 기본 UI 표시 |
|---|---|---|
| 직접 측정 | 사용자가 줄자/레이저 등으로 직접 측정해 입력 | 직접 측정 |
| 사진 보정 측정 | 사진에서 기준 길이를 지정해 계산한 값 | 사진 참고값 |
| 도면/제조사 참고 | 도면·설명서 등에서 확인한 값 | 문서 참고 |
| 미확인 | 출처 또는 측정 방법을 알 수 없음 | 출처 미확인 |

- `사진 보정 측정`을 `직접 측정`보다 높은 신뢰도로 표시하지 않는다.
- 사진 측정값은 오차 범위를 검증하기 전까지 오차 ±n mm 같은 수치를 임의로 표시하지 않는다.
- 사용자가 직접 확인해 값을 수정하면 `사용자 보정` 이력을 남기되, 최초 계산값도 감사/재검토용 메타데이터로 보존한다.
- 측정 출처가 없는 값이나 오래된 값은 비교 결과에 참고 경고를 표시한다.
- 비교 결과는 측정 방식이 섞여 있을 경우 각 치수별 출처를 각각 표시한다.

## 18.2 사진 보조 측정 1차 구현 UX

1. 측정 대상 상세에서 `사진으로 보조 측정`을 선택한다.
2. 사용 목적과 사진 저장 안내를 보여 준 뒤 카메라 또는 앨범을 연다.
3. 촬영 가이드: 측정할 경계가 잘 보이도록 정면 촬영, 기준물과 측정 대상은 같은 평면, 그림자/반사/흔들림 최소화.
4. 사진을 불러온 뒤 `기준 길이 표시` 단계에서 같은 평면의 기준선 양 끝을 터치한다.
5. 기준물의 실제 길이를 숫자로 입력하고 단위를 고른다.
6. `측정할 길이 표시` 단계에서 대상의 양 끝을 터치한다.
7. 계산 결과를 cm 단위로 표시하고 원본 기준 길이 및 픽셀/mm 값을 접어서 확인할 수 있게 한다.
8. 사용자가 결과를 수정하거나 수동 입력으로 전환할 수 있게 한다.
9. 저장 시 측정 방식, 기준 길이, 포인트 좌표, 사진 ID, 계산 버전을 함께 저장한다.
10. 결과 화면과 공간 상세에서 `사진 참고값` 표시와 `직접 재측정 권장` 문구를 노출한다.

## 18.3 핵심 기능 외 추가 제안 — MVP 우선순위

**MVP 포함 권장**
- 측정 대상별 체크리스트(예: 냉장고 자리: 가로/깊이/높이/좌우·후면·상단 여유, 세탁기 자리: 가로/깊이/높이/급배수/문 개방 공간, 소파: 제품 외형/현관문/복도/엘리베이터)
- 동일 공간에 제품 후보 최대 3개 비교
- 측정 기록 복제 및 수정
- 측정 출처·측정일·측정 방식의 명확한 표시
- 빈 공간·빈 측정 목록의 빠른 등록 템플릿
- 비교 스냅샷에서 당시 사용된 숫자와 사진을 보존

**MVP 이후 검토**
- 사각 기준물 4점을 지정하는 원근 보정
- 사진 위 화살표·선·텍스트 라벨 편집
- 앱인토스 환경에서 공식 지원이 확인된 경우 AR Depth 측정
- 검증된 File API를 이용한 측정 리포트/백업 파일 내보내기
- 가족/다른 기기 간 동기화(개인정보·인증·서버 비용·정책 검토가 선행되어야 하므로 현재 로컬 우선 MVP에서는 제외)

## 18.4 반드시 하지 말아야 할 구현

- 사진 픽셀 개수만으로 실제 길이를 계산하지 않는다. 반드시 사용자가 확인한 기준 길이를 요구한다.
- 사진 측정값을 자동 확정하거나 실제 실측값처럼 표시하지 않는다.
- 기준물과 대상이 다른 평면에 있는데 동일한 스케일을 적용하지 않는다.
- 이미지 분석을 외부 AI API로 전송하지 않는다.
- 브라우저 카메라 API로 SDK 권한 동의 흐름을 우회하지 않는다.
- 지원 여부가 불분명한 네이티브 브릿지·AR API를 임의로 구현하지 않는다.
- 검증하지 않은 사진 보정 정확도나 오차율을 광고/온보딩에 사용하지 않는다.
- 기기 변경·앱 삭제 후에도 데이터가 유지된다고 약속하지 않는다.
